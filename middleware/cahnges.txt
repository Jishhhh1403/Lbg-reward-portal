1. Executive summary

This specification defines the full five-agent extension required to turn individually relevant reward cards into a coherent, hyperpersonalised customer experience. It is written as a hand-off to a coding assistant and covers agent contracts, QUEST+R integration, state and schema changes, prompt requirements, orchestration, deterministic validations, reason codes, audit outputs, tests and phased implementation.

Core design principle

Personalisation determines what is relevant. Narrative orchestration determines what belongs together now, in what order, for which customer outcome, and how the experience continues after the customer acts.

The existing middleware remains the governance and compilation foundation. The extension preserves the current Consent Guardian, Risk Guardian, UI Constitution Guardian, Accessibility Agent, Component Planner, SDUI Compiler, Red-Team Challenger, deterministic Card Rule Engine and fallback behaviour. The new agents add explicit ownership of story, journey episodes, sequencing, coherence assurance and cross-session continuity.

New agent	Primary ownership	Stages	Authority
Customer Story Architect	One screen-level customer story, tension, resolution and intended outcome	U, E	Proposal; no veto
Journey and Mini-Journey Composer	Primary journey, episodes, entry/exit states and completion definition	E, S	Proposal; no veto
Narrative Sequence and Transition Agent	Card roles, order, dependencies, bridge logic and deferrals	S	Proposal; no veto
Experience Coherence Guardian	Coherence hard gate before selection and after compilation	E, S, R	VETO in E/S; HOLD in R
Session Continuity Agent	Resume, recap, resolve, branch, retire and stale-story handling	U, S, R	Challenge/HOLD recommendation
1.1 Definition of done
Five new agent modules are registered and visible in the health roster.
QUEST+R stage rosters and prompts invoke each agent in the specified stages.
QuestUIState carries typed story, journey, sequence, coherence and continuity artefacts.
Stage S maps components to an approved journey skeleton before final ordering.
The SDUI payload carries optional, backwards-compatible narrative metadata.
Deterministic post-processing cannot silently break the approved sequence; a post-compile coherence check runs in R.
Fallback and reason-code behaviour covers coherence failures.
Explainability records persist every new artefact and verdict.
Unit, graph, contract, regression and golden-scenario tests pass.
2. Current architecture and precise gap

The existing service fetches intelligence, applies deterministic card rules, builds shared state, executes Q→U→E→S→T→R, reconciles compiled components, validates the result and writes an explainability bundle. Stage S currently has a richness requirement of 12–17 components, persona breadth requirements, category coverage and deterministic mandatory stacks. These rules create breadth, but they do not require a single story or complete mini-journeys.

Gap statement

No current agent owns the end-to-end question:

“What coherent customer story should this screen tell, and how does every displayed component advance, explain, resolve or support that story?”

Existing role	What it does	What it does not own
Journey & Intent Agent	Classifies current journey, intent and phase	Does not author a screen-level story or episode structure
Personalisation Synthesiser	Scores candidate strategies	Does not score explicit narrative continuity today
Component Planner	Selects and configures registered cards	Does not own causal sequencing or journey closure
UI Constitution Guardian	Protects anchors, brand, tokens and legal surface	Does not validate semantic coherence
SDUI Compiler	Translates an approved plan mechanically	Must not make narrative decisions
Red-Team Challenger	Reviews broad failure and harm patterns	Does not provide a dedicated coherence contract
2.1 Target operating model

Customer intelligence + permitted evidence
→ current situation and intent
→ one approved customer story
→ one primary journey with 2–4 mini-journeys
→ registered components mapped to narrative roles
→ causal sequence and explicit transitions
→ governance + coherence gates
→ deterministic reconciliation
→ post-compile coherence assurance
→ session-aware continuation

3.1 Required execution order inside Stage S
Journey and Mini-Journey Composer produces the episode skeleton.
Component Planner maps only registered components to each episode and proposes alternatives.
Narrative Sequence and Transition Agent assigns roles, causal order, dependencies, transitions and deferrals.
Session Continuity Agent adjusts opening treatment and state-dependent content.
Accessibility Agent validates cognitive load and hierarchy.
UI Constitution Guardian validates anchors, registry constraints and brand/legal rules.
Experience Coherence Guardian validates the complete candidate and may veto.
Implementation warning

Do not ask the Component Planner to generate 12–17 cards first and retrofit a story afterwards. The journey skeleton must constrain component selection, not merely annotate it after selection.

4.1 Mission

Convert permitted customer context, current intent, goals, recent progress, reward state and continuity context into one screen-level story with a clearly bounded customer situation, genuine tension or opportunity, primary outcome and resolution. The story is a design contract, not marketing copy and not a psychological label.

4.4 Prompt contract
Objective

You are the Customer Story Architect in a governed banking rewards UI committee.

Create 2–3 evidence-grounded screen stories, then recommend one. Each story must define one primary customer outcome and an achievable, meaningfully advanceable resolution for this visit.

MUST
Use permitted evidence only and cite evidenceRefs.
Keep one primary outcome.
Express the story in one sentence.
Identify detours that would fragment the experience.
MUST NOT
Invent customer facts, goals or urgency.
Reinterpret the reward profile as personality.
Create campaign copy or regulated advice.
Use sensitive/protected attributes.
Lose sensitive/protected attributes.

Strict JSON matching StoryHypotheses.

4.5 Deterministic quality checks
Exactly 2–3 hypotheses.
Each evidenceRef resolves to permitted evidence.
Exactly one primaryOutcome per hypothesis.
oneSentenceStory is non-empty and below the configured length cap.
confidence is within 0–1.
completionSignals is non-empty.
No prohibited signal or protected attribute appears.
recommendedStoryId belongs to hypotheses.

5.1 Mission

Translate the approved story into one primary journey and two to four mini-journeys. Each mini-journey is a complete episode with an entry condition, customer question, purpose, required information, action or resolution, exit state and transition target. A heading is not a mini-journey.

    supportingSurfaces: list[SupportingSurface]

5.3 Prompt contract

Design a journey skeleton for the approved story before components are selected.

Every mini-journey must answer a distinct customer question and must end in an observable state.

Use 2–4 mini-journeys. Preserve one primary journey and one primary action at a time.

Move useful but non-essential information to supporting surfaces.

Do not name or invent component types. Do not convert generic content categories into episodes.

Return strict JSON matching ExperienceJourneyPlan.

5.4 Episode quality gate
Check	Requirement
Relevance	Episode directly advances the approved story
Completeness	Entry, development and exit are present
Continuity	Episode connects to preceding or next episode, unless explicitly optional
Necessity	Removing the episode would reduce utility or comprehension
Actionability	Requested action has a represented consequence
Scope	Episode does not introduce an unrelated primary journey
Evidence	Required information is supported by permitted evidence
6. Agent specification: Narrative Sequence and Transition Agent
Field	Specification
Stage	S
Message types	PROPOSAL
Veto authority	None
Primary output	narrativeSequence and deferredComponents
6.1 Mission

Order candidate components by causal and semantic relationship, assign each component a narrative role, define dependencies and bridge logic, and defer components that interrupt the approved journey. The agent may re-order or defer proposed components but may not invent unregistered components, customer facts or legal copy.

6.2 Narrative role enumeration
Role	Meaning
ORIENTATION	Establish current situation
MEANING	Explain why the situation matters
TENSION	Identify genuine gap, choice or opportunity
EVIDENCE	Provide relevant support
OPTION	Offer legitimate choice
ACTION	Enable the next step
FEEDBACK	Show the effect of a completed action
PAYOFF	Make immediate or future value visible
CELEBRATION	Show a genuinely triggered achievement
CONTINUATION	Preview the next episode
REFERENCE	Provide optional detail without interrupting the main path

6.4 Sequencing rules
POINTS_BALANCE remains the constitutionally anchored first component, but the first non-anchored card must establish the active story.
Every non-reference component must belong to exactly one mini-journey.
Every adjacent pair must have an explicit relationship or an episode boundary.
Only one component is designated as the dominant primary action.
An ACTION must be followed by FEEDBACK, PAYOFF or CONTINUATION in the same sequence or in the declared next state.
Generic educational or programme-mechanics cards become REFERENCE or supporting-surface content unless central to the approved story.
Untriggered celebration, stale actions and semantically orphaned cards are deferred.
7. Agent specification: Experience Coherence Guardian
Field	Specification
Canonical id	coherence-guardian
Suggested file	agents/coherence_guardian.py
Stages	E, S and R
Message types	APPROVAL, VETO, CHALLENGE
Authority	VETO in E/S; HOLD recommendation in R
Primary output	coherenceAssessment and postCompileCoherence
7.1 Mission

Protect the semantic integrity of the customer experience. The guardian votes that:

the journey is complete,
transitions are intelligible,
one dominant story is identifiable,
one primary action dominates,
each action has a consequence,
deterministic compilation has not broken the approved narrative,
intended outcomes remain connected,
and no mandatory component has fragmented the experience.
7.2 Assessment schema
class CoherenceAssessment(BaseModel):
    storyClarity: int = Field(ge=0, le=100)
    journeyContinuity: int = Field(ge=0, le=100)
    miniJourneyCompleteness: int = Field(ge=0, le=100)
    transitionStrength: int = Field(ge=0, le=100)
    actionOutcomeContinuity: int = Field(ge=0, le=100)
    contentDistractionRisk: Literal["Low", "High"]
    primaryActionClarity: Literal["PASS", "FAIL"]
    orphanComponents: list[str]
    conflictingNarratives: list[str]
    violations: list[CoherenceViolation]
    decision: Literal["PASS", "VETO", "HOLD"]
    reasonCode: str | None = None
7.3 Hard-gate conditions
No single story can be inferred from the approved artefacts or compiled screen.
More than one journey competes for primary attention.
The primary action is unrelated to the opening story context.
The action consequence is absent from the current or declared next state.
A mandatory component inserted after compilation breaks the main sequence.
One or more non-reference components are semantically orphaned.
Headings claim continuity that card relationships do not support.
A mini-journey begins but has no action, resolution or deliberate continuation.
The compiled SDUI materially differs from the approved narrative sequence.
The dominant action is visually or logically ambiguous.
7.4 Recommended thresholds
Configurable policy

The following values are implementation recommendations and should live in configuration rather than prompts.

PASS requires:

story clarity ≥ 75
journey continuity ≥ 70
mini-journey completeness ≥ 75
transition strength ≥ 65
action-outcome continuity ≥ 75
no HIGH distraction risk
no orphan component
primary-action clarity = PASS
8. Agent specification: Session Continuity Agent
Field	Specification
Canonical id	session-continuity
Suggested file	agents/session_continuity.py
Stages	U, S and R
Message types	OBSERVATION, PROPOSAL, CHALLENGE
Authority	No direct veto; may recommend HOLD

8.1 Mission

Maintain a purpose-bound experience state across visits and customer actions. The agent determines whether the customer should START, RESUME, RECAP, RESOLVE, BRANCH, RETIRE or RESTART a journey. It prevents repeated celebrations, stale actions, ignored dismissal signals and generic resets.

8.3 Privacy and retention guardrails
Use only session and event information approved by the Consent Guardian.
Do not build an unbounded behavioural history.
Every continuity attribute must have source, observedAt and expiry.
Dismissal is not a permanent negative preference unless explicitly declared.
Missing history means continuity unavailable, not “customer has no prior interest”.
Do not infer emotion, vulnerability or personality from abandonment or dwell time.
Retire stale stories when evidence, goal state or permission changes.

12.2 Important interaction with Card Rule Engine

The current deterministic engine can insert mandatory stacks after POINTS_BALANCE during post-processing. This remains binding.

To avoid silent fragmentation:

Expose mandatory stack directives to the Journey Composer and Narrative Sequencer before Stage S.
Assign every mandatory component a narrative role and mini-journey placement where possible.
When a mandatory component cannot belong to the primary journey, mark it REFERENCE and place it in the least disruptive permitted location.
After Stage T enforcement, run a deterministic narrative reconciliation that updates references and then let the Coherence Guardian review the actual compiled order.
Never remove a conduct-mandated component merely to improve storytelling.

13.1 Structural invariants
Components and priorities remain unique.
All story, journey, mini-journey and component references resolve.
Mini-journey orders are continuous and within the configured cap.
Dependencies point backwards in the rendered sequence unless explicitly asynchronous.
Exactly one primary action ID is present unless the charter explicitly allows none.
Every primary ACTION has a FEEDBACK, PAYOFF or CONTINUATION contract.
REFERENCE contents are optional and cannot become the dominant action.
Deferred components are absent from the main component list.
POINTS_BALANCE remains first as required by the existing constitution.

15.3 Golden scenarios
Active-first-home earning goal

Orient on goal, identify next gap, recommend one action, show points/goal payoff; defer generic programme content.

Customer completed action

RESOLVE CAP: opening shows feedback and newly unlocked next milestone; suppress recommended mode completed action card.

Customer dismissed a card

Do not repeat immediately; offer an alternate without inferring a permanent recommendation decline.

No continuity data

START mode; no negative inference; build only from current permitted content.

Select one primary story

Only one story should be selected even if multiple strategies are selectable; no competing mainlines.

Accessibility component cap

Reduce episode count/components while preserving orientation, action, consequence and comprehension.

Narrative sequence integrity

Never allow MEANING/REFERENCE to interrupt an active action path; route to the appropriate reference/supporting surface.

18. Engineering risks and mitigations
Risk	Mitigation
Reuse stage-level committee voting	Stage agency rises with veto lower response or more provider
Validators cache stale continuity context	Enforce bounded, stable continuity context
Prompt overlap between agents	Enforce “owns / must not own” boundaries
Too many relevant but unnecessary cards	Make journey requirements superior to breadth
Coherence engine changes order	Re-expose directives, reconcile metadata and run post-compile coherence
Continuity becomes surveillance	Purpose-bound, explainable, consented state and no sensitive inference; bounded history
Marketing copy becomes story	Keep separately rendered copy only
Variable educational value	Trigger only when it adds comprehension
Repeated experiences	Combine deterministic variant with configured thresholds and explicit violation codes
Backward incompatibility	Make narrative fields optional and preserve existing renderer behaviour
